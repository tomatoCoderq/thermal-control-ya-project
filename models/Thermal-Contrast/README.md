# Thermal-Contrast U-Net

Свернуть тепловое видео в четыре статических карты и подать их в обычный U-Net.

```
TermoDataset item (T, H, W)  →  extract_channels  →  (4, H, W)  →  U-Net  →  бинарная маска
```

Данные берутся из **всех** поддатасетов `datasets/datasets_list` — и `dataset_kaggle`,
и `dataset_tpu`.

## Каналы

`extract_channels(video) -> (4, H, W)` — единственная точка входа для признаков,
одна и та же на train, eval и inference.

| канал | формула | смысл |
|---|---|---|
| `maxmin` | max(t) − min(t) | тепловой контраст, классическая карта дефектов в NDT |
| `maxfirst` | max(t) − t₀ | пик нагрева относительно холодного базового кадра |
| `std` | σ по времени | насколько сильно пиксель «шевелится» за прогон |
| `pca1` | 1-я временная мода (EOF) | доминирующий режим нагрева/охлаждения (PCT / PPT) |

Кадры используются с двумя разными плотностями, и это сделано намеренно:

- `maxmin`, `maxfirst`, `std` считаются по равномерной выборке
  `ChannelParams.num_frames` кадров (по умолчанию 64) — для порядковых статистик
  этого достаточно, а извлечение остаётся дешёвым (~0.4 с на видео);
- `pca1` считается по **всем** оставленным кадрам, потому что доминирующая
  временная мода — свойство всего переходного процесса, а не его подвыборки.

PCA считается степенным методом на центрированной по времени матрице `(T, H·W)`.
Инициализация берётся из карты `maxmin`, поэтому результат детерминирован и
сходится за несколько проходов; знак сингулярного вектора произволен, так что он
разворачивается до положительной корреляции с `maxmin` — иначе дефекты случайно
получались бы то светлыми, то тёмными от видео к видео.

### Отбраковка кадров

Перед расчётом каналов выбрасываются два типа кадров (`select_frames`):

- **вспышка** — кадр яркий *и* пространственно плоский. Фотовспышка засвечивает
  матрицу равномерно и не несёт сигнала о дефектах, но, будучи самым ярким
  кадром прогона, полностью определяла бы `max(t)`.
- **аномальные ведущие кадры** — непрерывная серия с `t = 0`, у которой
  пространственный разброс сильно выше базового уровня до начала нагрева. Это
  калибровочные кадры камеры; если такой кадр оставить, `t₀` теряет смысл и
  канал `maxfirst` разрушается.

Порог яркости задаётся не в абсолютных единицах, а в долях амплитуды нагрева
`p99(mean) − median(mean)`, поэтому одни и те же числа работают и для сырых
отсчётов Kaggle (~7700), и для градусов TPU (~25).

На текущих данных правило вспышки не срабатывает ни разу (самые яркие кадры —
это информативная фаза нагрева с высоким пространственным контрастом), а правило
ведущих кадров убирает ровно то, для чего оно нужно: например, в `R_002.mat`
кадр 0 имеет mean 6412 против 7663 у кадров 1–10 и пространственную σ 423
против 42, и он отбрасывается; в `R_010.mat`, где кадр 0 нормальный, не
отбрасывается ничего.

### Нормализация

Каждый канал растягивается в `[0, 1]` по своему перцентильному диапазону
(1 % / 99 % по умолчанию).

Отдельно по каналам — потому что значения `pca1` лежат в другом масштабе, чем
разности температур, и общий диапазон сплющил бы часть каналов в почти
константные картинки.

По перцентилям, а не по min/max — потому что в кадре почти всегда есть что-то
намного горячее образца (оснастка, край панели). Один такой пиксель задаёт
максимум и загоняет весь образец в узкую полосу, из-за чего сетка дефектов
становится невидимой. На видео Kaggle обрезка по 1 %/99 % поднимает
contrast-to-noise дефектов с 0.35 до более 1.1 на худшем сэмпле.

## Кэш каналов

Извлечение детерминировано, поэтому оно выполняется один раз на видео, а
результат кладётся в `cache/<поддатасет>__<видео>__<ключ параметров>.npy`
(≈1 МБ на видео). Ключ — хеш `ChannelParams`, так что смена, например,
`num_frames` автоматически даёт другой набор файлов и старый кэш не подмешивается.

Первый прогон по 56 видео занимает ~25 с, дальше обучение стартует мгновенно.

## Обучение

```bash
cd models/Thermal-Contrast

python train.py --epochs 50                      # оба поддатасета
python train.py --epochs 50 --include dataset_tpu # только TPU
python train.py --epochs 50 --resume last         # продолжить прогон
```

Чекпоинты: `runs/contrast_best.pkl`, `runs/contrast_last.pkl`.
История: `runs/history.json` и `runs/metrics.csv`.

`.pkl` содержит не только веса, но и состояние оптимизатора и планировщика —
иначе возобновлённый прогон молча начинал бы со свежим AdamW и не тем learning
rate. Цена этого — размер файла: ~370 МБ на 31 млн параметров (веса плюс два
моментных буфера AdamW).

## Оценка и inference

```bash
python eval.py                     # таблица по test-видео + одна картинка
python eval.py --show -1           # только таблица
```

```python
from inference import load_trained_model, predict_mat
from common.device import get_device

device = get_device()
model = load_trained_model("runs/contrast_best.pkl", device)
result = predict_mat(model, "path/to/any.mat", device)
result["pred"]      # (256, 256) бинарная маска
result["channels"]  # (4, 256, 256) вход U-Net
```

`load_video_from_mat` повторяет препроцессинг `TermoDataset` шаг за шагом
(чтение `(H, W, T)` как float32 → перестановка в `(T, H, W)` → билинейный resize
до 256×256), поэтому незнакомое видео обрабатывается ровно так же, как обучающий
сэмпл. Совпадение проверяется побитово: `torch.equal(TermoDataset[i][0],
load_video_from_mat(path, mat_key))`. Если `mat_key` не задан, файл должен
содержать ровно один 3-мерный массив — так читаются и `data` (TPU), и
`imageArray` (Kaggle) без настройки.

## Что нужно знать про данные

Манифест `dataset_kaggle` объявлял `mat_key: "data"`, тогда как все 38 файлов
Kaggle хранят видео под именем `imageArray`. Из-за этого `TermoDataset` падал с
`KeyError` на каждом файле Kaggle, и все точки входа были захардкожены на
`dataset_tpu`. Исправлено в манифесте.

На обоих поддатасетах сетка дефектов в каналах видна и совпадает с GT — на
Kaggle отчётливее, на TPU слабее, но во всех 18 видео. Самый контрастный канал
на Kaggle — `std`.

На 18 видео TPU приходится всего 2 различных маски (12 и 6 файлов), то есть
маска описывает геометрию образца, а не конкретное видео; в Kaggle все 38 масок
различны.

Полезно знать про метрику: contrast-to-noise вида
`|mean внутри GT − mean вне GT| / σ вне GT` для этих данных плохой индикатор. В
знаменатель попадают тёмные полосы по краям кадра и горячая оснастка, σ которых
на порядок больше межпиксельного разброса на самом образце, поэтому величина
получается около 1.0 даже там, где сетка видна невооружённым глазом. Для оценки
информативности каналов смотрите картинки из
`contrast_channels_preview.ipynb`, а не только это число.
